## File Location

**Maven plugin.** The goals read `${project.basedir}/sigmund.yaml`, or the file given with
`-Dsigmund.trustConfig=<path>`. When the default file does not exist, `sigmund:verify` runs
without a policy and says so — it verifies and reports everything, failing only on a signature
that does not verify. A file given explicitly that does not exist is an error, so a mistyped
path cannot turn enforcement off.

**CLI.** Commands search, in order:

1. **Explicit path** — the `--config` flag
2. **Local config** — `./sigmund.yaml` in the current working directory
3. **User config** — `~/.config/sigmund/sigmund.yaml`

The **first file found wins**. Configuration files are not merged.

The top-level keys are `issuers`, `signers`, `artifact-sets`, `rules`, `defaults`, `signing`,
`verification` and `tools`. Any other key is an error, with the nearest known key suggested —
an ignored key would silently drop what you wrote. The same holds inside every section, and a
value of the wrong shape — a list where one value is expected, `"true"` for `true` — is an
error rather than read as something else. Values are read as written: only `true`, `false`,
`null` and plain numbers are typed, so `yes`, `on` and `~` are words, and `0x12345678` or `0123`
stays text rather than becoming a number. The file is read as YAML 1.2, as editors read it: under
YAML 1.1 an unquoted `0x12345678` would have reached a tool as the number `305419896`. Quote
fingerprints and key IDs anyway, as the examples do. The schema of earlier versions (`trust`,
`signature-optional`, `policy`, `artifacts`, `version`) is rejected with a message saying what
replaces it.

## Editor Support

Sigmund publishes a JSON Schema for `sigmund.yaml`, so editors with a YAML language server —
IntelliJ IDEA, and VS Code with the Red Hat YAML extension — complete keys, show what each
does, and flag unknown keys and wrong shapes while you type. Point the editor at it with a first
line naming the schema of the Sigmund version you use; a file generated by
`sigmund:dependency-signers` starts with it:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/cyberstamp/sigmund/<version>/core/src/main/resources/sigmund.schema.json
signers:
  alice:
    pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
```

Replace `<version>` with the release, such as `0.0.3`; the file at `main` is the schema of the
next release. In IntelliJ IDEA the same URL can instead be mapped to `sigmund.yaml` under
*Settings → Languages & Frameworks → Schemas and DTDs → JSON Schema Mappings*. The schema is
also inside `sigmund-core.jar`, as `sigmund.schema.json`.

The schema states keys and value shapes only. Sigmund itself remains the judge: that a rule
names a defined signer, that rules do not tie, and that a listed issuer can vouch for an entry
are checked when Sigmund loads the file, and a file the editor accepts can still fail there.

## Complete Example

```yaml
# Issuers trusted to vouch for identities in entries that name none
issuers:
  - keys.openpgp.org
  - https://token.actions.githubusercontent.com

# Identity registry — everyone policy or signing refers to
signers:
  # An organization with several release keys
  apache:
    members:
      - pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
        email: "dev@maven.apache.org"
      - pgp4: "BBE7232D7991050B54C8EA0ADC08637CA615D22C"

  # Keys already seen, plus an address for keys to come
  jane:
    pgp4: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"
    pgp6: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
    email: "jane@example.com"

  # A CI workflow, attested by a Sigstore certificate
  github-bot:
    identities:
      - source-repository-uri: "https://github.com/myorg/myrepo"
        build-config-uri: "https://github.com/myorg/myrepo/.github/workflows/release.yml@refs/heads/main"

  # An address, vouched for by a listed issuer
  jackson-dev: "tatu@fasterxml.com"

# Named groups of artifact patterns, for use in rules
artifact-sets:
  apache-stack:
    - "org.apache.maven.*"
    - "org.apache.commons.*"

# What each set of artifacts must satisfy
rules:
  - match: [apache-stack]
    requires: [apache]

  - match: ["com.fasterxml.jackson.*"]
    requires: [jackson-dev]

  # Both the release key and the CI workflow must have signed
  - match: ["com.example:mylib"]
    requires: [jane, github-bot]

  # Unsigned internal artifacts are tolerated; a signature on one is still checked
  - match: ["com.internal.*"]
    on-no-claim: ignore

# Policy-wide settings
defaults:
  extra-claims: reject
  on-indeterminate: warn

# Signing configuration
signing:
  signer: jane
  toolchain: [bc, sq, gpg]
  credential-types: [pgp4, pgp6]
  profiles:
    classic:
      - pgp4

# How verification runs — never what it accepts
verification:
  toolchain: [bc, sq, gpg]
  resolve-signers: true
  import-to-keyring: false
  keyservers:
    - hkps://keys.openpgp.org

# Tool-specific settings, used by both signing and verification
tools:
  bc:
    signing-fingerprint: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"
    passphrase-env: SIGMUND_BC_PASSPHRASE
    cipher-suite: ed25519
    gnupg-home: ~/.gnupg
    cert-d-home: ~/.local/share/pgp.cert.d
    bc-private-home: ~/.local/share/sigmund/bc-private
  sq:
    signing-fingerprint: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
    home: ~/.local/share/sequoia
    executable: sq
  gpg:
    signing-fingerprint: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
    executable: gpg
    home: ~/.gnupg
  sigstore:
    staging: false
    trusted-root: /path/to/trusted_root.json
    interactive: true
```

## Policy and Enforcement

The **policy** is the part of the file that decides what verification accepts: `issuers`,
`signers` as policy refers to them, `artifact-sets`, `rules` and `defaults`. The rest —
`signing`, `verification`, `tools` — configures how Sigmund runs. Only the policy can change
whether an artifact is accepted, and none of it can be set from the command line.

### When a policy is declared

A file **declares a policy** when it has a `rules` section — an empty `rules: []` included.
That single switch decides how strict verification is. `defaults` without `rules` is an error:
with no rule every artifact is `NOT_CONFIGURED`, so defaults alone could only fail everything
or change nothing, and adding them must not turn enforcement on by accident.

- **No policy** — a missing file, or one that only configures signing, tools or signers.
  Verification observes: every dependency is verified and reported, and only a signature that
  does not verify (`FAILED`) blocks the build. The goal logs that it is observing only.
- **A declared policy** enforces: every outcome other than `SATISFIED` blocks, unless the policy
  relaxes it. An artifact no rule matches is `NOT_CONFIGURED` and blocks too, which makes
  coverage a deliberate decision — add a rule, or a catch-all.

### Outcomes

Verification gives every artifact one outcome:

| Outcome | Meaning |
|---|---|
| `SATISFIED` | The matched rule's requirements are met |
| `UNSATISFIED` | Claims verified, but not from the signers the rule requires — or, under `extra-claims: reject`, also from a signer it does not name |
| `FAILED` | A signature does not match the artifact, or its key was revoked or had expired when it signed — or was revoked as compromised, at any time ([details](verification.md#outcomes-and-reasons)). The attack signal |
| `NO_CLAIM` | No signature or attestation was found |
| `INDETERMINATE` | Evidence exists but could not be checked: a key not available, an algorithm not accepted, a tool not working |
| `NOT_CONFIGURED` | No rule matches the artifact |

See [Trust Verification](trust-verification.md) for how claims roll up into these, and
[Signature Verification](verification.md#outcomes-and-reasons) for the reasons an outcome is
`INDETERMINATE`.

### How enforcement is resolved

Each outcome other than `SATISFIED` has an action:

- `fail` — the artifact blocks the build
- `warn` — it is reported as a warning
- `ignore` — it is counted in the report, and listed only with `-Dsigmund.detail`

The action is taken from the first of: the matched rule's own setting (`on-…` keys on the
rule), the policy's [`defaults`](#defaults), and the built-in default:

| Outcome | Setting | Built-in default |
|---|---|---|
| `FAILED` | — | `fail`, always; a setting for it is an error |
| `UNSATISFIED` | `on-unsatisfied` | `fail` |
| `NO_CLAIM` | `on-no-claim` | `fail` |
| `INDETERMINATE` | `on-indeterminate` | `fail` |
| `NOT_CONFIGURED` | `on-not-configured` | `fail` with a policy, `ignore` without |

Enforcement never changes an outcome. A report shows the same outcomes whether they blocked or
not, and an `ignore`d artifact is still verified — a signature that is present on it must still
verify.

## Section Reference

### `issuers`

**Type:** Array of issuer names  
**Default:** `[]` (empty)

The issuers trusted to vouch for identities in signer entries that do not name their own. This is the default grant for identities: a fingerprint needs no issuer, because the signature proves the key, but an email address or a CI workflow is only as good as whoever vouched for it.

Nothing is trusted unless the file lists it — not even keys.openpgp.org. A built-in grant would sit outside the file and its policy digest, and could change meaning between Sigmund versions. When bootstrap names a signer by an address keys.openpgp.org verified, it lists the directory here in the generated file instead, so the grant is reviewed with the policy and removed with one line.

```yaml
issuers:
  - keys.openpgp.org
  - https://token.actions.githubusercontent.com
```

Every issuer is an `https://` URL, and its kind is known from it, so it needs no configuration:

- **`https://keys.openpgp.org`** — a directory that publishes an address on a key only after the address owner confirms it. It vouches for `email`. As a known directory it may be written without the scheme, `keys.openpgp.org`.
- **Any other `https://` URL** — an OIDC issuer, proven through a Sigstore (Fulcio) certificate. It vouches for the certificate `subject`, `email` when the subject is an address, and the Fulcio certificate extensions listed under [`identities`](#object-form).

Any other name is an error when verification loads the policy. Signing does not check issuers, so a mistake here does not stop a release from being signed. Results always record the URL.

An entry may name its own `issuer` instead, which trusts that issuer for that entry only — it does not have to be listed. Listing an issuer makes it vouch for every entry that names none, so trusting an OIDC provider for one bot is better done inline. An entry that names no issuer must be assertable by exactly one listed issuer of a kind: when two listed OIDC issuers could both vouch for it, it is an error asking you to name the issuer on the entry.

### `signers`

**Type:** Map of signer ID → signer definition  
**Default:** `{}` (empty)

Defines the identity registry. Rules refer to signers by ID, and `signing.signer` names the identity to sign as. Each signer can be specified in multiple forms.

#### Minimal Form (Email Only)

A simple string value: an email address, vouched for by one of the listed [`issuers`](#issuers).

```yaml
issuers: [keys.openpgp.org]

signers:
  jackson-dev: "tatu@fasterxml.com"
```

#### Object Form

An object with credential fields. At least one credential must be specified, and unknown keys are errors — an ignored key would silently drop a credential.

```yaml
signers:
  jane:
    pgp4: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"                          # OpenPGP v4 fingerprint
    pgp6: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"  # OpenPGP v6 fingerprint
    email: "jane@example.com"                                                 # vouched for by a listed issuer
    identities:
      - issuer: "https://token.actions.githubusercontent.com"                 # optional; else the list
        source-repository-uri: "https://github.com/org/repo"
```

**Credential types:**

- **`pgp4`** — OpenPGP v4 fingerprint, the full 40 hexadecimal characters.
- **`pgp6`** — OpenPGP v6 fingerprint, the full 64 hexadecimal characters.

  Each takes one fingerprint or a list of them. A signer that rotated keys keeps every key it signed with, so its old signatures still verify:

  ```yaml
  signers:
    jane:
      pgp4: ["DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF", "CAFEBABECAFEBABECAFEBABECAFEBABECAFEBABE"]
      email: "jane@example.com"
  ```

  Fingerprints match exactly, ignoring case, against the key that made the signature or the primary key it belongs to. A 64-bit key ID is rejected at load: colliding key IDs can be generated, so a key ID would accept any key that shares it.

- **`email`** — An address, accepted only as vouched for by one of the listed [`issuers`](#issuers). To name the issuer, write it under `identities` instead.

  It matches, ignoring case, an address that a directory served for the signing key, or the address in a Sigstore certificate from that issuer. A user ID on an OpenPGP key is **never** matched on its own: anyone can put any address on a key they generate. When a key is not already pinned by a fingerprint, the directory is asked for the addresses it has verified for that key; if it cannot be reached, the artifact is `INDETERMINATE` (`key-unavailable`), never accepted.

  keys.openpgp.org serves OpenPGP v4 keys only, so it vouches for no address on a v6 key: a v6 key is accepted by its fingerprint, and a publisher's new v6 key needs adding by hand.

  An address is what lets a policy accept a key the publisher generates later. Its limit is that directory bindings are current state: after a publisher verifies the address for a new key, the directory serves the old key without it, so old signatures can no longer be tied to the address by a verifier that never saw them. Pair addresses with fingerprints — fingerprints for the keys already seen, the address for keys to come. What an address trusts is the directory's verification and the security of the email account.

- **`identities`** — A list of complete identities, each an `issuer` (optional; otherwise the listed [`issuers`](#issuers)) and the attributes that issuer must have attested. Only the attributes you name need to match, and at least one besides `issuer` is required. One signer may carry several, for example the same address from two issuers:

  ```yaml
  signers:
    alice:
      identities:
        - issuer: keys.openpgp.org
          email: "alice@example.com"
        - issuer: "https://accounts.google.com"
          email: "alice@example.com"
  ```

  What an entry may name depends on its issuer's kind. A directory attests `email` only. An OIDC issuer attests the certificate `subject`, `email` when the subject is an address, and the Fulcio certificate extensions:
  - `subject` — SAN subject (exact workflow+ref match, changes per release)
  - `source-repository-uri`, `source-repository-ref`, `source-repository-digest`, `source-repository-identifier` — the source repository
  - `source-repository-owner-uri`, `source-repository-owner-identifier` — its owner
  - `source-repository-visibility-at-signing`
  - `build-config-uri`, `build-config-digest` — the build configuration, e.g. the workflow file
  - `build-signer-uri`, `build-signer-digest` — the workflow that signed, when it differs
  - `build-trigger` — build trigger event (e.g., `release`, `push`)
  - `runner-environment` — runner environment (e.g., `github-hosted`)
  - `run-invocation-uri`, `deployment-environment`, `token-subject`

  A misspelled attribute is an error with the nearest known name suggested, never ignored: an ignored attribute would widen the match. So is an attribute the entry's issuers cannot attest, such as `source-repository-uri` from a directory.

  > **Stability versus precision:** `subject` carries the git ref, so it changes with every release. `source-repository-uri` is stable but alone accepts any workflow in the repository, including ones that are not the release pipeline; pair it with `build-config-uri`, and where it matters `build-trigger` and `runner-environment`.

  > **Signing-time matching:** When the signer is used for signing (`signing.signer`), the OIDC token is checked before a Fulcio certificate is requested against every entry whose issuer is an OIDC issuer — an entry without its own `issuer` uses the top-level `issuers`: its issuer always, and its subject too when the entry names a `subject`. A token matching no entry is refused before Fulcio is asked. Every attribute, the certificate extensions included, is then checked on the issued certificate before the signature is written, so a signature that does not prove the signer never reaches the output; verification checks them again.

#### Organization with Multiple Members

When a signer represents an organization, use the `members` array to list individual signing keys. A member may carry any credential a signer can; nested `members` are not allowed.

```yaml
issuers: [keys.openpgp.org]

signers:
  apache:
    members:
      - pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
        email: "dev@maven.apache.org"
      - pgp4: "BBE7232D7991050B54C8EA0ADC08637CA615D22C"
```

### `artifact-sets`

**Type:** Map of set name → array of [artifact patterns](#artifact-patterns)  
**Default:** `{}` (empty)

Names a group of patterns so rules can refer to it. A set is a label only: a rule that names
it matches exactly as if it listed the set's patterns.

```yaml
signers:
  apache:
    pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"

artifact-sets:
  apache-stack:
    - "org.apache.maven.*"
    - "org.apache.commons.*"
    - "org.apache.httpcomponents.*"

rules:
  - match: [apache-stack]
    requires: [apache]
```

A word in `match` with no `.`, `:` or `*` is always a set name, and one that is not defined is
an error with the nearest set suggested — otherwise a misspelled set would quietly become a
group pattern matching nothing.

### `rules`

**Type:** Array of rules  
**Default:** none — and without `rules` there is [no policy](#when-a-policy-is-declared)

Each rule says what the artifacts it matches must satisfy:

```yaml
signers:
  acme-release:
    pgp4: "9B1C0E7F2D4A6B83C5E1F09A7D3B2C4E6F8A0B1D"
  acme-ci:
    identities:
      - issuer: "https://token.actions.githubusercontent.com"
        source-repository-uri: "https://github.com/acme/widget"
  acme-ci-eu:
    identities:
      - issuer: "https://token.actions.githubusercontent.com"
        source-repository-uri: "https://github.com/acme/widget-eu"

rules:
  - match: ["com.acme.*"]
    requires: [acme-release, {any-of: [acme-ci, acme-ci-eu]}]
    on-indeterminate: warn
```

#### Fields

- **`match`** (required) — an [artifact pattern](#artifact-patterns) or
  [artifact-set](#artifact-sets) name, or a list of them. The rule matches an artifact when any
  of them does.
- **`requires`** (optional) — a signer ID, or a list of clauses, **all** of which must be
  satisfied. A clause
  is a signer ID, satisfied by a verified claim proving one of that signer's credentials, or
  `{any-of: [...]}`, satisfied by any one of the listed signers. So
  `[acme-release, {any-of: [acme-ci, acme-ci-eu]}]` reads "acme-release, and acme-ci or
  acme-ci-eu", and `requires: acme-release` is the same as `[acme-release]`. An empty list is
  an error — a rule that tolerates artifacts says so through its `on-…` settings instead. `any-of` entries are signer IDs and
  cannot nest. Signer IDs must be defined under `signers`.
- **`on-unsatisfied`**, **`on-no-claim`**, **`on-indeterminate`**, **`on-not-configured`**
  (optional) — `fail`, `warn` or `ignore` for this rule's artifacts, overriding
  [`defaults`](#defaults). See [How enforcement is resolved](#how-enforcement-is-resolved).
- **`extra-claims`** (optional, `reject` or `ignore`) — this rule's handling of a verified claim
  from a signer it does not name, overriding [`defaults`](#defaults). One rule can accept
  surplus signers without loosening the whole policy.

#### Which rule applies

**The most specific rule wins**, and only that rule applies — nothing is merged across rules,
so the rule a result names explains it fully. Specificity is decided by the
[pattern](#artifact-patterns) that matched.

**Two rules must not tie.** If patterns of two different rules have equal specificity and some
coordinate matches both, the policy is rejected when verification loads it, naming both rules
and such a coordinate:

```
Rules tie on specificity: rules[0] 'com.acme:*:1.0' and rules[1] 'com.acme:lib' both match com.acme:lib:1.0; make one more specific or merge them
```

The check is conservative: it also rejects a tie whose shared coordinates a more specific third
rule would always take, so that a verdict never depends on the order rules are written in.

#### Rules without `requires`

A rule may leave `requires` out, typically a catch-all or a rule for artifacts known to be
unsigned. It matches, so its artifacts are not `NOT_CONFIGURED`, but it requires no signer:

- an **unsigned** artifact is `NO_CLAIM` — relax it with `on-no-claim: ignore`;
- a **signed** artifact is `UNSATISFIED` under the default `extra-claims: reject`, because its
  signer is one no clause names. Tolerate those too with `on-unsatisfied: ignore`, or give the
  artifact a rule of its own.

### `defaults`

**Type:** Object  
**Default:** `extra-claims: reject`, built-in enforcement

Policy-wide settings, for every rule that does not set its own. `defaults` needs `rules`: on
its own it is an error, since it would apply to no rule (see
[When a policy is declared](#when-a-policy-is-declared)).

```yaml
rules:
  - match: "org.apache.*"
    on-no-claim: ignore

defaults:
  extra-claims: reject
  on-no-claim: warn
  on-indeterminate: warn
```

#### Fields

- **`extra-claims`** (`reject` or `ignore`, default `reject`) — what to do with a verified claim
  from a signer no clause of the matched rule names, once the requirements are already met.
  `reject` treats the rule's signers as the complete list and makes such an artifact
  `UNSATISFIED`; `ignore` records the claim and lets the requirements decide. It never applies to
  a claim that fails — that is always `FAILED`.
- **`on-unsatisfied`**, **`on-no-claim`**, **`on-indeterminate`**, **`on-not-configured`** —
  `fail`, `warn` or `ignore` for every rule that does not set its own. There is no `on-failed`.

A rule may set `extra-claims` and the `on-…` keys itself, which overrides these.

### `signing`

**Type:** Object  
**Default:** No signer, no toolchain configured

Configures which identity to sign as and the signing toolchain. Signing uses only `signing`,
`signers` and `tools`. The policy's own checks — that rules name defined signers, that issuers
are known, that rules do not tie — run only when verification loads it, so a mistake there does
not stop a release from being signed. A file that is not well-formed — invalid YAML, an unknown
key, a malformed rule — fails every command.

```yaml
signers:
  my-identity:
    pgp4: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"
    pgp6: "CAFEBABECAFEBABECAFEBABECAFEBABECAFEBABECAFEBABECAFEBABECAFEBABE"

signing:
  signer: my-identity             # Asserts who signs; does not choose the key
  toolchain: [bc, sq]             # Tools to use for signing, in priority order
  credential-types: [pgp4, pgp6]  # Default credential types to produce
  profiles:                       # Named profiles for explicit switching
    classic:
      - pgp4

tools:
  bc:
    signing-fingerprint: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"   # the v4 key bc signs with
  sq:
    signing-fingerprint: "CAFEBABECAFEBABECAFEBABECAFEBABECAFEBABECAFEBABECAFEBABECAFEBABE"   # the v6 PQC key
```

Each tool signs with the key its own settings select — `signing-fingerprint`,
`SIGMUND_BC_SIGNING_KEY`, or the tool's own default; see [Signing](signing.md). `signer` then
checks every signature against the signer, so each key a run signs with must be one of the
signer's credentials: here the v4 classic signature proves `pgp4`, and the v6 PQC signature can
only prove a pinned `pgp6`, since directories do not vouch for v6 keys.

#### Fields

- **`signer`** (string, optional) — References a signer ID from the `signers` section. Asserts who signs: every signature a run produces must prove this signer, or signing fails naming the expected and the proven credential. It does not choose the key; each tool's own settings do. A name not defined under `signers` is a load error, and so is an identity entry of that signer no issuer can satisfy — an `email` with no listed `issuers`, a misspelled attribute, or an attribute its issuer cannot attest — checked at load for this signer only, as verification checks every signer. For OpenPGP, the signing key must be pinned by the signer's `pgp4`/`pgp6` fingerprints or confirmed by a directory for one of the signer's addresses, as in verification; with `verification.resolve-signers: false` no directory is asked, so only pinned keys pass. With `verification.resolve-signers: true` (the default), signing may also reach the network for keys: a fresh signature the tool that produced it cannot verify itself is verified by another tool of the same format, which may fetch the signing key from a keyserver.
- **`toolchain`** (array of strings, optional) — Lists which tools to use for signing and in what order: the tools that may sign, each of which must be available. Which of their keys sign is decided by `credential-types` or a profile. Only the listed tools are initialized. Tool names: `bc`, `sq`, `gpg`, `sigstore`; any other name is an error when tools are built. Per-tool settings are configured in the top-level `tools` section.
- **`credential-types`** (array of strings, optional) — The default set of credential types to produce. The types select keys, not tools: each tool signs with its keys of a listed type, and a tool left with none does not sign. A listed type no key in the run covers fails before anything is signed (`no signing key for requested credential type <type>; keys in the run: ...`), as does a key whose type cannot be read. A `toolchain` tool with no key of a listed type does not sign, which is not an error. When omitted, every key of every available signing tool signs. Values: `pgp4`, `pgp6`, `sigstore` — the names signer entries use; any other value is an error.
- **`profiles`** (map, optional) — Named profiles for explicit switching (e.g., `--profile classic`). Each profile maps a name to a list of credential types, the same values as `credential-types`; any other value is an error. Profiles select keys the same way. When a profile is requested by name, it takes precedence over `credential-types`.

### `verification`

**Type:** Object  
**Default:** See fields below

Configures how verification runs: which tools check claims, and where keys are fetched from.
These settings change what Sigmund can see, never what it accepts — a wider keyserver list can
turn a `key-unavailable` into a verdict, but cannot make an untrusted artifact pass. Which
cryptographic algorithms are accepted is fixed in Sigmund and the same for every tool; see
[Accepted algorithms](verification.md#accepted-algorithms).

```yaml
verification:
  toolchain: [bc, sq, gpg]
  resolve-signers: true
  import-to-keyring: false
  keyservers:
    - hkps://keys.openpgp.org
```

#### Fields

- **`toolchain`** (array of strings, default: `[bc, sq, gpg]`)

  Lists which tools to use for verification and in what order. When specified, **only** the listed tools are initialized, and a name no tool has is an error. When omitted, all available tools are initialized in the default order (`bc`, `sq`, `gpg`). Tool-specific settings are configured in the top-level `tools` section. The tools reach the same verdict for the same signature; the order decides which answers first.

- **`resolve-signers`** (boolean, default: `true`)

  Whether to fetch missing keys from keyservers, and to ask directories named in `issuers` for the verified addresses of keys a policy entry needs. When `false`, a signature whose signer can only be established through a directory is `INDETERMINATE` (`key-unavailable`). When `true` and a key is not found locally, tools attempt to fetch it from the configured keyservers. The behavior depends on the tool and `import-to-keyring`:

  | `resolve-signers` | `import-to-keyring` | BC | GPG | SQ |
  |---|---|---|---|---|
  | `false` | any | no fetch | no fetch | no fetch |
  | `true` | `false` (default) | fetch ephemerally (in-memory, discarded after build) | skip (GPG cannot do ephemeral imports) | no fetch |
  | `true` | `true` | fetch + persist to cert-d | fetch + persist to GPG keyring | no fetch |

  `sq` never fetches keys: it uses only the certificates already in its own store.

  When `resolve-signers: true` but no tool in the configured toolchain can fetch keys (e.g., only GPG with `import-to-keyring: false`), Sigmund logs a warning.

  A per-keyserver circuit breaker prevents slow builds when offline — after the first connection failure to a keyserver, all subsequent fetch attempts to that server are skipped. A per-key negative cache prevents re-querying the same missing key across artifacts.

- **`import-to-keyring`** (boolean, default: `false`)

  Controls how fetched keys are stored. Only meaningful when `resolve-signers` is `true`:

  - `false` (default) — Keys are cached in memory for the session. BC supports ephemeral key storage; GPG does not, so key fetch is skipped entirely for GPG when this is `false`.
  - `true` — Keys are permanently imported into the tool's keyring (BC cert-d or GPG keyring).

  **Note:** `keys.openpgp.org` serves a key without its user IDs until the owner verifies an address. Without the self-signatures on its user IDs, the key cannot be validated, so its signatures are `INDETERMINATE` (`key-unavailable`); a fuller copy from another keyserver resolves them. GPG refuses to import such a key at all.

- **`keyservers`** (array of strings, default: `[hkps://keys.openpgp.org]`)

  Keyserver URLs for fetching missing keys, asked in order. The first copy that carries user IDs is used; a copy without them is used only when no keyserver has a fuller one. The result records which keyserver supplied the key. Keyservers supply key material only: the signature proves the key whoever served it, and a user ID a keyserver serves never becomes an identity — identities come only from [`issuers`](#issuers). That is why this is safe to change from the command line.

  ```yaml
  verification:
    keyservers:
      - hkps://keys.openpgp.org
      - hkps://keyserver.ubuntu.com
  ```

### `tools`

**Type:** Map of tool name → tool settings  
**Default:** `{}` (empty)

Configures per-tool settings used by both signing and verification. All tool-specific configuration lives here, so `signing` and `verification` only name tools.

```yaml
tools:
  bc:
    signing-fingerprint: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"
    passphrase-env: MY_BC_PASSPHRASE
    gnupg-home: ~/.gnupg
    cert-d-home: ~/.local/share/pgp.cert.d
  sq:
    home: ~/.local/share/sequoia
    signing-fingerprint: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
    executable: sq
  gpg:
    signing-fingerprint: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
    home: ~/.gnupg
    executable: gpg
```

Keys are tool names (`bc`, `sq`, `gpg`, `sigstore`). Values are tool-specific settings, each a single value except `signing-fingerprint`, which may also be a list, documented in the [Tool Settings Tables](#tool-settings-tables) below. For example, `tools.bc.signing-fingerprint` is used by signing, while `tools.bc.gnupg-home` is used by verification.

`bc`, `sq` and `gpg` all select their signing key with `signing-fingerprint`, a full fingerprint. A
key ID, an address or a user ID can name more than one key, so any other value is an error when
tools are built — also for a tool no toolchain names. Without the setting, each tool falls back
to its own default key, listed in its table; [`signing.signer`](#signing) then checks that the
key used is the signer's.

`signing-fingerprint` may also be a list, which makes the tool sign with each key; the list must be
non-empty and name no fingerprint twice, and `gpg` accepts v4 fingerprints only:

```yaml
tools:
  sq:
    signing-fingerprint:
      - "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
      - "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
```

Tool names and settings are checked when tools are built, by the tools themselves: an unknown
tool, or a setting its tool does not accept, is an error naming the nearest one — a misspelled
setting would otherwise leave the tool on its default. The same check applies to the tool names
in `signing.toolchain` and `verification.toolchain`. `sigstore` is a tool only when
`sigmund-sigstore` is on the classpath; see [Enabling Sigstore Support](maven-plugin.md#enabling-sigstore-support).

## Artifact Patterns

Rules match on group, artifact and version — the Maven coordinates of a module. Classifier and
extension are not part of a pattern: every file published under one coordinate (jar, pom,
sources, javadoc) comes from the same module build, so one rule covers them all, while each file
is still verified and reported on its own.

| Pattern | Matches |
|---|---|
| `org.example` | every artifact in group `org.example` |
| `org.example.*` | group `org.example` and every group below it — `org.example.sub` — but not `org.examplefoo` |
| `org.example:lib` | artifact `lib`, every version |
| `org.example:lib:1.0` | that version only |
| `org.example:lib-*` | artifacts whose name starts with `lib-` |
| `org.example:lib:1.*` | versions starting with `1.` — `1.0`, `1.2.3` — but not `10.0`, nor a bare `1` |
| `*` | everything: a catch-all, the least specific pattern |

An omitted part matches anything, and a part may be `*`. On the group, `.*` is a subtree that
includes the group itself. On artifact and version, a trailing `*` is a plain prefix of
everything before it, dot included. A pattern with more than three parts is an error, since a
classifier-scoped pattern would silently match nothing. Quote a pattern that starts with `*` —
in YAML a bare `*` starts an alias.

A word with no `.`, `:` or `*` is an [artifact-set](#artifact-sets) name. To match a group whose
name is a single word, write `junit:*`.

**Specificity.** When several rules match, the one whose matching pattern is most specific
wins. The group counts most, by its number of segments, an exact group beating the `.*` subtree
of the same name; a named artifact beats a prefix, which beats any; a version adds the same way.
`org.example:lib:1.0` beats `org.example:lib`, which beats `org.example`, which beats
`org.example.*`, which beats `*`.

## Tool Settings Tables

### BC (BouncyCastle)

Configured in the top-level `tools.bc` section.

| Setting | Default | Description |
|---------|---------|-------------|
| `gnupg-home` | `tools.gpg.home` when set, else `~/.gnupg` | GnuPG home directory for reading `pubring.kbx` (or legacy `pubring.gpg`) |
| `cert-d-home` | `~/.local/share/pgp.cert.d` | Shared OpenPGP cert-d directory for public certificates — the store `sq` uses by default, so each tool sees the certificates the other stores |
| `bc-private-home` | `~/.local/share/sigmund/bc-private` | BC private key store directory, kept outside the shared cert-d |
| `signing-fingerprint` | (none) | Full fingerprint of the key to sign with, or a list of them to sign with each: 40 hex characters for a v4 key, 64 for v6, the key's type coming from the length. Ignored when a key comes from `signing-key-env` or `tsk-file`, which sign with the first key they hold only |
| `tsk-file` | (none) | Path to an exported Transferable Secret Key (TSK) file for signing |
| `signing-key-env` | `SIGMUND_BC_SIGNING_KEY` | Environment variable name containing the ASCII-armored private key. For ephemeral CI runners. |
| `passphrase-env` | `SIGMUND_BC_PASSPHRASE` | Environment variable name containing the passphrase. If not set, falls back to interactive prompt. |
| `cipher-suite` | `ed25519` | Algorithm `sigmund keygen` generates when `--cipher-suite` is not given (see supported values below) |

**Supported cipher suites (BC):**

- `ed25519` — EdDSA with Curve25519 (default)
- `ed448` — EdDSA with Curve448 (v6 only)
- `rsa4096` — RSA with 4096-bit modulus
- `nistp256` — ECDSA with NIST P-256 curve (v4 only)
- `nistp384` — ECDSA with NIST P-384 curve (v4 only)
- `nistp521` — ECDSA with NIST P-521 curve (v4 only)

Keys are v4 unless `sigmund keygen --credential-type pgp6` asks for v6: keys.openpgp.org serves
only v4 keys, and GnuPG signs and verifies only v4. BC does not generate post-quantum keys;
generate them with [SQ](#sq-sequoia).

**Passphrase resolution order:**

1. Explicit `PassphraseProvider` via API (`Sigmund.Builder.bcPassphraseProvider()`)
2. Environment variable specified by `passphrase-env` setting
3. Interactive console prompt (if a terminal is available)
4. No passphrase (works only for unencrypted keys)

**Example:**

```yaml
tools:
  bc:
    signing-fingerprint: "ABCDEF1234567890ABCDEF1234567890ABCDEF12"
    passphrase-env: MY_BC_KEY_PASSPHRASE
    cipher-suite: ed448
    gnupg-home: /custom/gnupg
    cert-d-home: /custom/cert-d
```

### SQ (Sequoia)

Configured in the top-level `tools.sq` section.

| Setting | Default | Description |
|---------|---------|-------------|
| `home` | `~/.local/share/sequoia` | Sequoia home directory for keys and certificates |
| `executable` | `sq` | Path to the `sq` executable (if not on `PATH`) |
| `signing-fingerprint` | `sign.signer-self` in sq's config | Full fingerprint of the key to sign with, or a list of them to sign with each: 40 hex characters for a v4 key, 64 for v6, the key's type coming from the length. `sign.signer-self` holding several keys signs with the first only |

Sigmund runs `sq` under its own crypto policy, which replaces the host's system policy for those
runs; see [Accepted algorithms](verification.md#accepted-algorithms).

**Cipher suites:** keys for `sq` are generated with `sq key generate` itself, not through
Sigmund; see [Generating a PQC Key](signing.md#generating-a-pqc-key).

Sequoia supports the post-quantum hybrid cipher suites of RFC 9980, which extends OpenPGP v6 (RFC 9580):
- `mldsa87-ed448` — ML-DSA-87 + Ed448 (default)
- `mldsa65-ed25519` — ML-DSA-65 + Ed25519
- Additional suites supported by `sq key generate --cipher-suite`

**Example:**

```yaml
tools:
  sq:
    home: ~/.local/share/sequoia
    signing-fingerprint: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
    executable: /usr/local/bin/sq
```

### GPG (GnuPG)

Configured in the top-level `tools.gpg` section.

| Setting | Default | Description |
|---------|---------|-------------|
| `executable` | `gpg` | Path to the `gpg` executable (if not on `PATH`) |
| `signing-fingerprint` | `default-key` in `gpg.conf`, else the first secret key | Full fingerprint of the key to sign with, or a list of them to sign with each: 40 hex characters, since gpg signs with v4 keys only (a 64-hex fingerprint is an error). Each is passed to `--local-user`; a primary key's fingerprint signs with its signing subkey |
| `home` | (system default) | GnuPG home directory (`--homedir` option). Also the default `gnupg-home` of [BC](#bc-bouncycastle), so both tools read the same keyring |
| `passphrase-env` | `SIGMUND_GPG_PASSPHRASE` | Environment variable name containing the passphrase. If not set, falls back to `gpg-agent`. |

**Note:** GPG only supports OpenPGP v4 keys. OpenPGP v6 keys cannot be used with GPG.

**Example:**

```yaml
tools:
  gpg:
    signing-fingerprint: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
    home: ~/.gnupg
    executable: /usr/bin/gpg2
```

### Sigstore

Configured in the top-level `tools.sigstore` section. Sigstore uses OIDC-based keyless signing via `sigstore-java` — no long-lived keys to manage.

| Setting | Default | Description |
|---------|---------|-------------|
| `staging` | `false` | Use the Sigstore staging instance instead of production. For testing only. |
| `trusted-root` | (none) | Path to a custom `trusted_root.json` file. When omitted, the root is fetched via TUF from the Sigstore public-good instance. |
| `interactive` | `false` | Allow interactive OIDC browser login. When `false`, only ambient credentials are used: the `SIGSTORE_JAVA_ID_TOKEN` environment variable (if set), then GitHub Actions OIDC. Set to `true` for desktop signing. |

The Sigstore tool is pure Java (provided by the `sigmund-sigstore` module) and does not require any external CLI binary. It is ServiceLoader-discovered — adding the module to the classpath is sufficient.

**Credential type:** `sigstore`  
**File extension:** `.sigstore.json`

**Example:**

```yaml
tools:
  sigstore:
    interactive: true
```

## Common Configuration Patterns

### Minimal Verification Policy

One signer, one rule. Anything the rule does not match is `NOT_CONFIGURED` and fails, so start
with [Gradual Adoption](#gradual-adoption) if your dependencies are mostly unsigned.

```yaml
signers:
  apache:
    pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"

rules:
  - match: ["org.apache.*"]
    requires: [apache]
```

### Publisher Key and CI Identity Together

Accept an artifact only if both the publisher's release key and the project's release workflow
signed it — a stolen key alone, or a compromised workflow alone, is not enough.

```yaml
signers:
  acme-release:
    pgp4: "9B1C0E7F2D4A6B83C5E1F09A7D3B2C4E6F8A0B1D"
  acme-ci:
    identities:
      - issuer: "https://token.actions.githubusercontent.com"
        source-repository-uri: "https://github.com/acme/widget"
        build-config-uri: "https://github.com/acme/widget/.github/workflows/release.yml@refs/heads/main"

rules:
  - match: ["com.acme.*"]
    requires: [acme-release, acme-ci]
```

### Tolerating Unsigned Artifacts

Internal artifacts are published unsigned. They are still verified, so a signature that is
present on one must verify; only a missing one is tolerated.

```yaml
signers:
  apache:
    pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"

rules:
  - match: ["org.apache.*"]
    requires: [apache]
  - match: ["com.internal.*", "com.example:test-utils"]
    on-no-claim: ignore
```

### Gradual Adoption

Require signers where you know them, and see everything else without failing the build. The
catch-all reports every other artifact as a warning — unsigned (`NO_CLAIM`) or signed by someone
no rule names (`UNSATISFIED`) — so the report shows what is left to cover.

```yaml
signers:
  apache:
    pgp4: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"

rules:
  - match: ["org.apache.*"]
    requires: [apache]
  - match: ["*"]
    on-no-claim: warn
    on-unsatisfied: warn
```

`sigmund:dependency-signers -Dsigmund.generateTrustConfig` writes a starting policy from the
signatures your dependencies carry today; see [Maven Plugin](maven-plugin.md).

### CI/CD Signing Config

```yaml
signing:
  toolchain: [bc]

tools:
  bc:
    signing-fingerprint: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"
    passphrase-env: CI_SIGNING_KEY_PASSPHRASE
```

### Multi-Tool Hybrid Signing

```yaml
signers:
  release-team:
    pgp4: "DEADBEEFDEADBEEFDEADBEEFDEADBEEFDEADBEEF"                          # v4 key, for GPG compatibility
    pgp6: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"  # v6 key, for PQC

signing:
  signer: release-team
  toolchain: [bc, sq, gpg]
  credential-types: [pgp4, pgp6]

verification:
  toolchain: [bc, sq, gpg]

tools:
  bc:
    signing-fingerprint: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
    cipher-suite: ed448
  sq:
    signing-fingerprint: "1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF"
  gpg:
    signing-fingerprint: "4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12"
```

### Sigstore-Only Signing

```yaml
signing:
  toolchain: [sigstore]
```

No tool settings needed — ambient OIDC credentials from GitHub Actions are used automatically.

To have verification accept the artifacts by that workflow identity, define it as a signer and
require it in a rule. A signer alone is never consulted: without a rule, or with no `rules` or
`defaults` at all, verification only observes.

```yaml
signers:
  ci-bot:
    identities:
      - issuer: "https://token.actions.githubusercontent.com"
        source-repository-uri: "https://github.com/myorg/myrepo"

rules:
  - match: ["com.myorg.*"]
    requires: [ci-bot]

signing:
  signer: ci-bot
  toolchain: [sigstore]
```

### Mixed OpenPGP + Sigstore Signing

```yaml
signers:
  release-lead:
    pgp4: "ABCDEF1234567890ABCDEF1234567890ABCDEF12"
    identities:
      - issuer: "https://token.actions.githubusercontent.com"
        source-repository-uri: "https://github.com/myorg/myrepo"

rules:
  - match: ["com.myorg.*"]
    requires: [release-lead]

signing:
  signer: release-lead
  toolchain: [bc, sigstore]

verification:
  toolchain: [bc, sigstore]

tools:
  bc:
    signing-fingerprint: "ABCDEF1234567890ABCDEF1234567890ABCDEF12"
    passphrase-env: BC_PASSPHRASE
  sigstore:
    trusted-root: /etc/sigmund/trusted_root.json
```

This produces both a `.asc` (OpenPGP) and a `.sigstore.json` (Sigstore bundle) for each artifact. Under the rule, the `.asc` proves `release-lead` by the fingerprint and the bundle by the workflow identity; either satisfies the rule, and both are checked.
