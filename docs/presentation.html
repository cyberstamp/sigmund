1 Motivation

The Dependency Trust Gap

Maven Central requires PGP signatures for publishing. Community tools like pgpverify-maven-plugin verify signatures and can pin expected fingerprints to artifacts via keysMap — a real step forward.

But fingerprint pinning operates at a lower level than trust. It can confirm which key signed an artifact, but can't answer: who is behind that key, and do I trust them across different signing systems? The gap is between cryptographic verification and identity-based trust.

Fingerprint pinning ≠ identity trust PGP-only, single paradigm
1 Motivation

A Fragmenting OpenPGP Ecosystem

GnuPG chose to follow LibrePGP rather than the IETF standard. Sequoia PGP implements RFC 9580. Both handle v4 keys, but their next-generation formats diverge: LibrePGP defines v5 keys, RFC 9580 defines v6 keys — the two are incompatible.

v4 is the common ground, but GnuPG will never support v6 and Sequoia will never support v5. A tool that bridges both ecosystems needs to work with all of them.

GnuPG → LibrePGP (v4 + v5) Sequoia → RFC 9580 (v4 + v6) v5 ≠ v6 — incompatible
1 Motivation

Post-Quantum Cryptography Is Arriving

RFC 9980 defines hybrid PQC+classical signatures — ML-DSA-87+Ed448 combined in a single OpenPGP packet. Sequoia sq 1.4.0+ already implements it. This isn't theoretical.

No Maven signing tool is ready for post-quantum cryptography.

ML-DSA-87 + Ed448 RFC 9980 Sequoia sq 1.4.0+
1 Motivation

Sigstore and PGP Need to Coexist

Maven Central now validates Sigstore alongside PGP. Some projects sign with PGP, others with Sigstore, many will do both during the transition. Consumers need to verify dependencies regardless of which system the publisher chose.

No existing Maven tool unifies both paradigms under a single trust model. A project that depends on PGP-signed and Sigstore-signed artifacts needs two separate verification tools with no way to express unified trust policies across them.

Mixed ecosystems are the reality One trust model for both Cross-backend identity matching

The Key Difference: Fingerprints vs. Identities

◆ pgpverify keysMap

Maps artifacts to raw fingerprints. You need to know and manage key IDs directly. PGP-only — each signing system requires a separate tool.

# keysMap.list io.quarkus = 0x4AEE18F83AFDEB23 org.apache.maven = 0xBBE7232D7991050B, 0x2D7BAF3C1E9F5A12 com.internal:util = noSig

◆ Sigmund sigmund.yaml

Maps artifacts to named signer identities with multiple credential types. One config covers PGP, Sigstore, and future backends.

# sigmund.yaml signers: quarkus-team: name: "Quarkus Team" pgp4: "4AEE18F83AFDEB23..." pgp6: "D62AAB339E45E5EA..." email: "quarkus-dev@..." trust: io.quarkus.*: quarkus-team

Complementary, not competing

pgpverify-maven-plugin is a solid, mature plugin (10+ years, actively maintained) that fills a real gap in PGP signature verification. Sigmund takes the next step by lifting verification from the fingerprint level to the identity level — answering not just "was this signed by key X?" but "was this signed by Alice, across any of her keys and signing systems?" — while also unifying signing and verification across multiple backends.

2 Purpose & Approach

Identity-First, Not Signature-First

✅

Sigmund's approach

"Is this artifact from someone I trust?"

Signatures are evidence, not the end goal

A signer is a named entity with a credential bag — fingerprints, emails, OIDC identities, Sigstore certificate fields. Trust policies map artifact patterns to expected signers. Identity matching is type-agnostic: credential overlap works across OpenPGP, Sigstore, and any future backend.

What Sigmund replaces & adds

  • Replaces maven-gpg-plugin, sign-maven-plugin, and sigstore-maven-plugin — one plugin for all signing and verification needs
  • Adds identity-based dependency trust verification — a capability no other Maven tool offers
  • Hybrid PQC + classic signing in one .asc — backward-compatible with existing verifiers
  • Multi-format signing: .asc + .sigstore.json in a single build
  • Four backends: BC (pure Java), Sequoia (PQC), GnuPG (legacy), Sigstore (keyless OIDC)
  • Auto-generate trust config, then enforce in CI

Try it — no POM changes needed

# See who signed your dependencies mvn dev.cyberstamp.sigmund:sigmund-maven-plugin:0.0.1:dependency-signers # Generate trust config from actual signatures mvn sigmund:dependency-signers -Dsigmund.generateTrustConfig=true # Enforce trust policies mvn sigmund:verify

Credential Model

Identity matching is type-agnostic. Each credential type handles its own matching semantics.

FingerprintCredential

Types: openpgp4, openpgp6

Named by key version, not tool or algorithm. Exact fingerprint match.

EmailCredential

Type: email

Cross-backend fallback. Case-insensitive. Works across OpenPGP and Sigstore.

SigstoreCredential

Type: sigstore

Rich matching on Fulcio cert extensions. Null fields act as wildcards.

Cross-Backend Identity Matching

Sigstore verification extracts both a SigstoreCredential and an EmailCredential. A signer configured with only an email matches both OpenPGP and Sigstore signatures — no cross-type matching logic needed.

4 Sigstore Integration

How Sigmund Integrates sigstore-java

Architecture

Separate sigmund-sigstore module isolates heavy dependencies. SigstoreToolFactory is ServiceLoader-discovered — adding the JAR to the classpath is sufficient.

Wraps KeylessSigner and KeylessVerifier from sigstore-java. Pure Java, no CLI binary needed.

Signing Safeguards

OIDC identity validation during signing via allowedOidcIdentities — prevents artifacts from being signed with the wrong identity. Signing fails if the OIDC token doesn't match the expected identity.

CI-tuned defaults: ambient GitHub Actions OIDC token, no browser popups in non-interactive environments.

SigstoreCredential: Rich Certificate Matching

Sigstore verification extracts credentials from Fulcio certificate extensions. Each field is independently matchable — null fields act as wildcards.

◆ Subject matching (fragile)

The OIDC subject often includes version-specific refs that change with every release. Trust config requires updates on every dependency version bump.

# Breaks on every new release tag sigstore: issuer: "https://token.actions.githubusercontent.com" subject: "https://github.com/org/repo/.github/workflows/release.yml@refs/tags/v1.2.3"

◆ Source repo URI matching (stable)

The source-repository-uri points to the repository itself — stable across versions. Trust config stays static: "trust anything signed from this repo."

# Stable across all versions sigstore: issuer: "https://token.actions.githubusercontent.com" source-repository-uri: "https://github.com/org/repo"

Cross-Backend Identity Matching

One signer, both worlds

When a Sigstore signature is verified and the Fulcio certificate subject is an email, Sigmund extracts both a SigstoreCredential and an EmailCredential. A signer configured with just an email credential matches PGP and Sigstore signatures transparently — no cross-type matching logic needed.

This means a project migrating from PGP to Sigstore can keep the same trust config — the email-based matching bridges both systems automatically.

Credential-to-Tool Routing

The builder routes signer credentials to tools in three steps:

1

Capability Match

Find tools whose supportedCredentialTypes() contains the credential type.

2

Availability Check

canSign() filters tools that don't have the key material in their keyring.

3

Ambiguity Resolution

Single survivor wins. Multiple survivors → config error. Explicit tools.*.credentials overrides bypass all of this.

Backward-Compatible Hybrid .asc

Classic signature is always the first armored block. Tools that parse only the first block (including Maven Central) see only the classic signature and succeed. PQC-aware tools process all blocks.

v4 block BC → NO_KEY → sq → SKIPPED → GPG finds key in pubring.kbx → PASS
v6 block BC → NO_KEY → sq finds key in cert store → PASS

Trust Verification Flow

TrustVerifier.assess() goes beyond crypto validity to answer: "Is this artifact from someone I trust?"

1

Resolve Policy

Look up expected signers for the artifact from sigmund.yaml trust mappings. Pattern matching with wildcard support and specificity ranking.

2

Check Unsigned Allowances

If the artifact matches an unsigned: pattern and has no evidence → immediately return TRUSTED.

3

Verify Evidence

EvidenceProvider.verify() → EvidenceResults with proven credentials. Key fetching from keyservers happens transparently here on NO_KEY results.

4

Match Identity

Credential bag overlap: any proven credential matches any expected credential → identity confirmed. Type-agnostic — works across all backends.

5

Apply Policy → Verdict

Produce the final trust verdict based on matches and policy settings.

Trust Verdicts

TRUSTED UNTRUSTED UNSIGNED VERIFICATION_FAILED NOT_CONFIGURED
TRUSTED — expected signer matched
UNTRUSTED — signed but not by expected signer
UNSIGNED — no evidence files found
VERIFICATION_FAILED — crypto failure
NOT_CONFIGURED — artifact not in policy
7 Impact

What This Means for Maven

▶ For Consumers

  • First tool to verify who signed your dependencies
  • Enforce trust policies automatically in CI
  • Auto-generate config from existing signatures
  • Cross-backend: one signer matches OpenPGP + Sigstore

▶ For Publishers

  • Drop-in replacement for existing signing plugins
  • PQC-ready today — future-proof without breaking consumers
  • Multi-format: .asc + .sigstore.json in one build
  • Pure Java BC backend — zero external deps

▶ For the Ecosystem

  • Bridges the LibrePGP / RFC 9580 split
  • Identity-first model extensible to SLSA, SBOM verification
  • EvidenceProvider SPI for future trust evidence types
  • SignatureToolFactory SPI for new signing backends
